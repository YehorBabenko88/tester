Reviewed 2026-11-07. Scope: documentation-only assessment for standalone Trader Intelligence in YehorBabenko88/tester. ## Account history versus anonymous market prints

An address-filtered execution feed can support a public account history; an anonymous market trade feed cannot establish which account traded. Account/wallet identifiers identify protocol accounts, not verified humans, a person's complete portfolio, or ownership across services. Keep identity namespace and venue/network in every key. Do not join wallets to human names, contact details or inferred cross-platform owners. These are proposed product boundaries, not claims made by the providers.

## Hyperliquid: candidate, capped history

The official Info schema documents POST https://api.hyperliquid.xyz/info with JSON type/user, without signing or API-key fields. This supports a technical public-read classification, not a tested authorization result. userFills returns up to 2,000 latest fills; userFillsByTime returns up to 2,000 and exposes only the latest 10,000. Bounds are inclusive epoch milliseconds. The generic pagination note says 500 elements/distinct blocks, while this method specifies 2,000; retain the discrepancy and never assume one universal cap. Pagination uses the last returned timestamp; overlap/deduplicate boundary fills and detect no progress. aggregateByTime changes row granularity. Supply the real master/subaccount address, not an agent wallet; empty output is otherwise possible. Preserve coin/dex identity, tid/hash/oid and original financial strings. [Official Info endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint).

IP-wide REST budget is 1,200 weight/minute. These fill requests fall under default info weight 20, with additional weight per 20 returned items. Budget across shared workers and respect provider backoff; do not multiply IPs/accounts to evade limits. [Official rate limits](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/rate-limits-and-user-limits).

No fixed API indexing/publication-lag guarantee was found in the reviewed fill documentation. Keep execution time separate from observed_at, received_at and first_available_at. Do not infer publication time from execution time. The official historical-data page warns of missing data and untimely monthly archive updates; it describes book/context archives and links an independently maintained third-party user-history export, not an unlimited official user-fill archive. No AWS transfer or third-party export was attempted. [Official historical data](https://hyperliquid.gitbook.io/hyperliquid-docs/historical-data).

Technical registration/signing is not indicated for these documented reads; any applicable account/territorial/usage terms still require a separately recorded review. [App terms](https://app.hyperliquid.xyz/terms), [Foundation terms route](https://hyperfoundation.org/termsofservice).

## Polymarket: relevant public-wallet feed, version and rights gates

Use current Data API v2. Official migration guidance says v1 retired November 2, 2026; old /trades offset examples are obsolete for a new integration. v2 uses /v2/trades, data/pagination envelope, snake_case and opaque cursors; obsolete offset/market parameters are rejected. [Official v1→v2 migration](https://docs.polymarket.com/migrate/data-api-v1-to-v2).

Data API v2 explicitly says its routes need no API key/token. The shared docs say feed cursors are keyset-based; resend identical filters each page because the cursor does not bind them. Responses may use empty data or null for documented misses. A 429/503 may carry Retry-After. This is public read access, distinct from authenticated CLOB order/account operations. [Official Data API v2 documentation](https://data-api.polymarket.com/v2/docs), [API surfaces and authentication](https://docs.polymarket.com/getting-started/api).

GET /v2/trades supports user=address, page size up to 1,000, and cursor continuation anchored on block_timestamp/sequence_id. Per-user start/end use inclusive epoch seconds: omitted start defaults to three years; start=1 requests stored full history, not proof of complete lifetime activity. Bare feed has a shorter window and is not interchangeable. taker_only defaults true; false includes maker rows. Size filtering defaults 0.01, and zero retains that default. Thus defaults exclude some wallet activity; retain filters in provenance. Response includes proxy_wallet, condition/token IDs, transaction_hash, side, size, price and timestamp; a transaction hash alone need not uniquely identify an execution. Preserve number tokens exactly before conversion. [Official List trades](https://docs.polymarket.com/api-reference/feeds/list-trades).

Published IP limits: v2 overall 800 requests/10s, trades 300/10s, status 100/10s. These are ceilings, not recommended polling rates; use a deliberately lower S0 budget and backoff. [Official rate limits](https://docs.polymarket.com/api-reference/rate-limits).

GET /v2/status reports serving freshness, ingestion positions, computed_at and age_seconds from a background snapshot. It can reveal a stalled projection; this is not a guaranteed historical per-trade publication timestamp or SLA. Record the status snapshot alongside observation time and retain stale/unavailable status rather than treating absence as zero. [Official data freshness](https://docs.polymarket.com/api-reference/service/get-data-freshness).

**Rights status: REQUIRES_REVIEW / permission gate for specified uses.** Current official terms, effective August 11, 2026, restrict data access/use by defined Capital Market Clients and market-data distributors unless agreed in writing, including API/onchain and raw/derived/aggregated/anonymized data. They also restrict commercial exploitation/redistribution to those recipients without written agreement. Do not infer a general data license from no-auth access or an OpenAPI MIT label. S0 must identify intended entity/use/recipient scope and retain actual written permission before enabling a restricted production/distribution use. This is the provider's stated condition, not a definitive legal determination for this project. [Official Terms of Use](https://polymarket.com/tos).

## Safe S0 registry recommendations

Register Hyperliquid info/userFillsByTime and Polymarket Data API v2/trades as separate documentation-reviewed candidates, with acquisition disabled until exact intended use and applicable rights are recorded. Technical access may be PUBLIC_NO_AUTH_DOCUMENTED; rights must remain separate UNVERIFIED/REVIEW_REQUIRED, never implied APPROVED. No public-address collection is necessary to establish S0.

For each source retain canonical docs/terms URLs, reviewed_at, endpoint/version, account namespace, registration/auth description, budget model, history cap/default window, pagination/filter semantics, source timestamp unit, precision, publication-lag evidence, rights scope and review expiry. Endpoint migration or terms changes invalidate the prior review. Public-source account IDs should come only from explicit user-selected addresses or documented/public protocol examples; do not enumerate or deanonymize accounts.

For any later authorized bounded pilot: fix one address and bounded time window, low request/page/byte budgets and a hard stop; persist original response bytes/hash plus request filters/cursors/counts/terminal condition and ingestion run. Deduplicate overlap using documented identity, retaining ambiguity when no unique execution key is established. Decode JSON financial numbers without binary float loss. Same timestamp saturation, cursor loop, cap or unknown start means PARTIAL/UNVERIFIED, not COMPLETE. Null/empty means unavailable/no observed records under those filters, never verified inactivity. A completed page walk proves only exhaustion of the served query, not lifetime account history.

Keep API availability, collection coverage, account identity confidence and licensing permission as four independent statuses. Product labels should say public protocol account or wallet activity, include observed date range and exclusions, and avoid performance/profit claims based on censored histories, missing deposits/transfers/fees or mixed maker/taker defaults. No trading, copying, execution integration or connection to another runtime is authorized by this source audit.
