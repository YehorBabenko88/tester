# Fresh Tester lab installer

This proposal operates exclusively under `C:\TesterLab`, API loopback18766 and dedicated PostgreSQL55470. It never adopts a ProgramData marker or an existing service. No source files are patched after publication. Preparation accepts only a new empty root, a full Git commit SHA, and the exact relative-file SHA256 inventory independently produced from its published archive. Tests may use isolated scratch roots; physical SCM entrypoints accept only `C:\TesterLab`.

`.tester-lab.json` uses schema `tester-lab/v1`: random installation UUID, repository, absolute root, UUID-derived app/PostgreSQL service names, ports, retained release inventories and active SHA. Reparse paths and foreign markers are refused. Source bytes reside in `releases/<SHA>`; runtime, state, dependencies, PostgreSQL data, private secrets and backups live outside releases.

The bootstrap prepares a private complete CPython installation, venv and compatible pywin32 wheel. `stage_service_runtime(root)` copies the private CPython stdlib/DLLs and private `pythonservice.exe`/`pywintypes` DLL, then stages published startup hooks. The entire private standard library and both hooks are precompiled with the bootstrap interpreter and inventoried, including caches needed before startup customization. Therefore bootstrap and private CPython must have matching major/minor versions. Registry `PythonClass=lab_service_bootstrap.LabService` loads a top-level private shim before any immutable source package. The shim and startup sitecustomize disable bytecode before release imports; the service runtime inventory includes their existing caches.

The app is a real pywin32 `ServiceFramework` hosted by private `pythonservice.exe`, with its private venv supervisor suspended until assigned to a kill-on-close Job Object. `src.api.supervisor` owns API/worker drainage. Service readiness remains START_PENDING until the API returns healthy database/worker/storage/provider status and echoes this launch's random 32-hex instance token. An unexpected supervisor exit, startup readiness timeout or graceful-stop timeout reports a service-specific failure. Startup cancellation kills the bounded job; normal stop requests supervisor drainage, waits32seconds and kills remaining descendants through job closure.

Both services use LocalService and Manual startup; automatic recovery is intentionally not configured. The app depends on its installation's dedicated `pg_ctl runservice` service. Exact binary images, account, installation UUID and root are verified before any mutation; app registration additionally pins source SHA. PostgreSQL binary inventory, exact dedicated config, lack of ALTER SYSTEM overrides and recorded cluster system identifier are checked before installation/start. No PostgreSQL5432 endpoint is contacted.

`Manage-TesterLab.ps1` never self-elevates. Mutations require an explicitly opened administrator shell and an externally approved `-ManifestSHA256` for `state/deploy-payload.json`. Native PowerShell verifies that manifest and the full source inventory before importing Python. `status` uses ordinary read access and SCM CONNECT/query rights. ACL installation clears inherited and prior explicit grants only inside the owned root; original individual creator, LocalService and administrators receive distinct grants. The creator retains source/runtime diagnostic reads; immutable source/dependencies are read/execute; LocalService may modify runtime/PG data; private admin secrets and backups remain administrator/System only. A root owned by a built-in privileged group is refused rather than guessing the original creator.

After root bootstrap and publication verification, the concrete registration action is:

```powershell
& 'C:\TesterLab\releases\<PUBLISHED_SHA>\scripts\windows\Manage-TesterLab.ps1' -Action install -ManifestSHA256 '<APPROVED_EXTERNAL_PAYLOAD_SHA256>'
```

Review and pin the actual script SHA256 and external manifest hash before UAC. `start`, `stop`, `restart` and `remove` use the same script/manifest arguments; `status` needs neither elevation nor a manifest argument. The script only registers on install; start is separate and reviewable. Status includes configured SHA, exact service image/account/PID and runtime launch evidence. Runtime evidence is an observation, not a replacement for matching API instance/health verification.

Portable lifecycle APIs: `prepare`, `check`, `stage_release` (`add_release` alias), `rollback`, `remove` in `src.api.lab_install`. Stage only a new exact SHA directory and retain previous releases. Existing registrations must be exactly owned/stopped for staging. Activation/rollback requires services deregistered to prevent registry/source divergence, selects only inventoried retained bytes, then config frontend path must select that release before re-registration. Removal deregisters only existing exact-owned stopped registrations, archives marker state, and retains every source release, dependency, runtime datum, PostgreSQL file and backup. It never recursively deletes. A partial app-registration failure leaves an explicit SCM installation journal; explicit remove can recover an exact-owned stopped PostgreSQL-only registration. Unknown partially created foreign registrations are refused for manual inspection.

Verification: focused unit/security tests cover unknown roots, tampered inventories, traversal, real scratch junction rejection, random ownership, exact image/account/SHA ownership, backup retention, stage/rollback, private runtime inventory, a real isolated interpreter import proving no source bytecode writes, health-token format, PG config overrides, PG identity mismatch before any registration, and partial-registration recovery. Native Windows SCM, LocalService ACL execution, real service startup/drainage and recovery after actual host failures still require the separately approved published-payload physical acceptance run. No such actions were performed during implementation.
