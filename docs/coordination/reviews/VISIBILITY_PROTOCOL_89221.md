# Architecture challenge: prospective visibility fences

Scope: tester only, architecture/review criteria. No proposed B implementation was examined or approved here. Current B a8aa exports timing facts without issuing a visibility certificate; retaining UNAVAILABLE is appropriate until a complete prospective protocol is implemented and tested. No repository/host/physical database actions were performed; only this report was written.

## Evidence and exact claim

Inspected ROOT's retained visibility-counterexamples.json and accompanying script in docs/coordination/evidence. They report actual owned-PostgreSQL demonstrations that DEFAULT now() can precede cutoff while its row is still uncommitted, and that an RR snapshot established before acquiring a lock still excludes a writer committed before the lock was acquired. Those are ROOT's executed results; this reviewer did not rerun PostgreSQL.

A sufficient narrow claim is: **named immutable snapshot S contains exactly the governed facts visible in database snapshot V, and those captured facts were observed visible no later than an explicitly bounded observation time U.** Record the governed scope and proof dependencies. This is not an exact commit timestamp, proof that no fact ever existed earlier, exchange publication time, or an arbitrary historical-asOf query. A snapshot captured after cutoff cannot retroactively prove it was available before cutoff merely because its source rows contain old timestamps. Legacy history cannot be backfilled with invented visibility times.

## Minimum invariants to demand from B

1. **Gate before snapshot.** Acquire observer ownership using a session/control operation outside the RR transaction, then create a fresh RR transaction and actually establish its data snapshot. A blocking advisory-lock SELECT inside an already-open RR transaction may establish the stale snapshot it was intended to protect. Configuration/metadata SELECTs before lock acquisition are relevant too. Reused/pool connections must prove no pre-existing transaction/snapshot. SQL statement order and autocommit boundaries must be explicit and tested.

2. **Every relevant writer participates.** Observer exclusion must wait for all admitted writers to finish COMMIT/ROLLBACK; a writer must retain its gate through the actual commit, not just until its last INSERT or Python context body. Gate source writes, provenance/run/evidence relations, empty/negative acquisition facts, availability/coverage assertions, incidents, resolutions, quarantine/unquarantine, archive registration/repair and metadata affecting interpretation. Migration/repair/import/direct runtime SQL paths cannot be omitted. All-table proof-affecting mutations need an enumerated inventory and enforceable privilege/trigger/API boundary. A cooperative convention cannot honestly certify arbitrary writes by a privileged actor who bypasses it.

3. **Scope closure.** Instrument-local locks are sufficient only if every dependency is instrument-local. Shared archives, cross-scope incidents, global policy/schema changes and source/run evidence spanning instruments require either a common gate or a deterministic complete multi-scope gate set. The observer must not discover additional dependency locks after its snapshot. Define lock order with existing migration/recovery/scope locks; test deadlocks, starvation, cancellation and pool/session reuse. One simple common gate is easier to review than an incompletely closed per-instrument optimization.

4. **Recompute proof inside the protected snapshot.** A named fence must bind requested range, full supporting batches (including support outside the requested subrange), record identity/content digests, source observations, run declarations, evidence, negative facts, active incidents/resolutions, quarantine and archive manifests/bytes. Preserve current strict completeness/cadence/future-horizon checks; do not convert a historical verified flag into a visibility certificate. A row-only digest without missing/negative evidence cannot prove acquisition completeness.

5. **Separate source visibility, snapshot capture and publication.** transaction_timestamp/DEFAULT now remain transaction-start facts. Sampling clock_timestamp after establishing the protected snapshot can provide a conservative observation bound for source visibility; sampling before a blocking gate cannot. Manifest construction, database commit, file durability and client receipt happen later and need separate facts. A timestamp written into a manifest before its commit does not prove the manifest itself was visible/durable by that timestamp. If consumers use the certificate as information at cutoff, require evidence of its own publication/observation by cutoff, not only old source visibility. Avoid an endlessly recursive claim that every seal's precommit timestamp proves that seal's publication.

6. **Immutable named result, not a live alias.** Persist an installation/database identity and fresh capture epoch, snapshot/fence ID, exact scope/ranges, protocol/validator/schema versions, byte/count budgets, dependency identity/digest inventory and clock semantics/uncertainty. The captured result or all needed immutable versions must remain recoverable. A manifest containing only mutable query instructions is insufficient. Do not resolve a named historical fence through today's live coverage/source tables and call the result the original snapshot.

7. **External bytes have their own consistency boundary.** PostgreSQL RR does not freeze filesystem archives. Immutable content-addressed objects must be pinned and checked consistently with snapshot manifests; repairs/replacement/quarantine/reference changes must participate in the same admitted-writer protocol or use independently immutable generations. Hashing an object outside the gate and attaching its hash to a later manifest opens a race. File rename, PostgreSQL commit and filesystem durability are not one atomic operation; partial publication must remain unavailable and preserve prior evidence.

8. **Crash-safe publication and recovery.** Define draft/materialized/sealed/usable states with a single authoritative publication transition. Timeouts, serialization failures, incomplete hashes, budget exhaustion, lost locks/connections, restart and mismatched manifest digests must never expose a usable partial snapshot. Release session locks on every path and prove pooled sessions cannot keep stale ownership. Resume cannot adopt an orphan file or partial ledger solely from its filename. Database restore/clone requires new capture identity or explicit restore lineage; a copied timestamp/ID alone is not a certificate of this installation's historical observation.

9. **Truthful clocks.** State that U is a database/local observation bound, not a universally synchronized time. Detect/reject backward clock movement or implausible clocks relative to protocol invariants; capture ordering/epochs and clock health separately. Monotonic time is suitable for local duration budgets but cannot be silently serialized as UTC or compared across restarts/hosts. No track_commit_timestamp or global server configuration change is needed to make the narrow prospective observation claim.

10. **Postcapture incidents and reuse.** A new fact cannot rewrite the immutable old snapshot, but it must invalidate reuse as current truth. APIs must distinguish explicitly named historical state from current integrity/availability. A stale fence is not authorization to mark today's range COMPLETE, and historical COMPLETE means what the governed evidence established then, not guaranteed eternal correctness. Current missing/quarantined archive bytes may prevent replay even if their former visibility was recorded. A later negative finding must not be hidden behind an older named certificate.

## Acceptance cases before considering a usable protocol

- ROOT's delayed-commit and RR-before-lock counterexamples, reproduced against the actual proposed capture API, must fail closed or wait for the correct snapshot.
- Writer begins before gate/cutoff, blocks until after cutoff, then commits; writer commits while observer is waiting; commit acknowledgement is delayed; rollback never publishes a fact.
- Provenance/evidence/negative-result/incident/resolution/quarantine/archive repair changes under observer capture, including cross-instrument dependencies and direct permitted SQL paths.
- Crash after gate, after snapshot, mid-materialization, after file write, before/after manifest commit and before response; cancellation/timeout/pooled connection reuse and lost-lock takeover.
- Reopen the named snapshot after new rows, new incidents, new source runs and archive loss; distinguish immutable historical replay from prohibited stale-current promotion.
- Clock steps backward/forward, exact cutoff boundary, database restart/restore/clone, legacy rows without authentic prospective capture, and missing/unbounded support.
- Verify mutation-free capture where promised, or explicitly enumerate its own manifest writes. Internal manifest publication must not deadlock by trying to reacquire an incompatible writer gate already held by its observer.

These are review criteria, not approval or a recommendation to implement a broad scheduler. The smallest viable next step is one explicitly named prospective capture under a demonstrably common writer/observer boundary, with bounded persisted materialization and conservative unavailable behavior elsewhere. Arbitrary historical-asOf remains unsupported.

## Review of the actual B proposal, 89221f2

Read exact docs/storage/prospective-visibility-receipts.md at commit 89221f2ecc20827e9d15e40de6e39ab51c0456d0. It is explicitly a proposal; no successful production path was implemented. Its before-RR session gate, atomic immutable capture/result, post-commit fresh confirmation, conservative ceil time, receipt commit plus fresh lookup, declared negative universe and DATABASE_FACTS_ONLY archive exclusion directly address the two demonstrated counterexamples. It correctly refuses arbitrary historical reconstruction and does not backdate receipt publication.

**Technical recommendation: safe to proceed with a LIMITED foundational schema/epoch/common-gate prototype and executable interleaving tests only.** Keep production knowledge_time UNAVAILABLE and all C quality_available_at/provider defaults disabled. This recommendation is not approval of a usable receipt, enforcement completeness, UTC attestation, or production historical success. Before implementation, make the following acceptance conditions part of the prototype contract:

- **Two availability bounds, not one overloaded value.** observed_by_ms is an upper bound on durable visibility of the exact capture/result, sampled after re-read. The receipt itself becomes available only after its later commit and fresh lookup/consumer observation. C currently treats quality_available_at as availability of the supplied whole quality snapshot/provenance, not merely a source row's possible existence. Do not directly map the earlier capture bound onto a snapshot that includes a receipt/evidence reference created later. An online decision replay must require its actual needed certificate and all inputs available by cutoff; conservatively use the later independently observed publication bound. A retrospective proof of potential capture availability is a different, explicitly labeled research/audit claim, not proof a historical decision had that receipt. Keep both facts in separate typed fields, and do not compute a late receipt's publication time from its INSERT timestamp.
- **Trusted upper-bound clock remains a real prerequisite.** Ceiling PostgreSQL's microsecond sample to milliseconds prevents rounding early; it does not correct a slow or unsynchronized host clock. Define clock-domain identity, offset/uncertainty policy and how the upper bound incorporates uncertainty. Monotonic elapsed checks detect some jumps but cannot establish UTC correctness across hosts/restarts. Unknown health, rollback or unsupported forward-jump policy must leave certification unavailable. Unit traces alone cannot establish this trust.
- **Restore epoch cannot rely solely on copied DB identity.** A physical restore/clone can retain PostgreSQL system_identifier, epoch rows, receipt rows and logical generations. Require a reviewed external installation/restore lineage or enrollment authority and rotate/re-enroll on known restore/clone before current-state certification. Do not claim universal detection of an administrator silently restoring all state. Historical named artifacts may remain auditable under their old lineage; they cannot automatically certify the restored installation's current state.
- **Generation changes must be atomic and scoped exhaustively.** Advance the governed source/quality generation in the same transaction as every admitted mutation, including negative acquisition facts and quarantine/resolution changes. Failed/rolled-back writes must not produce usable new state. Cross-scope changes need the same gate or closed deterministic gate set. Define whether duplicate idempotent writes advance generation and distinguish receipt-internal bookkeeping from proof-affecting facts so capture publication does not invalidate itself or deadlock. Freshness means matching that exact admitted universe, not equality of a row count or timestamp.
- **Implementation order must enforce the claim before exposing it.** The schema can record only disabled/prototype epochs initially. The common gate needs role/entrypoint enforcement and a complete mutation-path inventory before any epoch is eligible for certificates. An advisory-lock helper with one ungated repair, migration, direct runtime write or filesystem-dependent quality path is insufficient. All snapshot establishment must happen after successful gate acquisition; pooled connections must start fresh.
- **Archive exclusion must propagate into validation and C.** DATABASE_FACTS_ONLY cannot certify a quality claim whose validation requires historical physical archive health. Its validation_result must declare precisely which stronger predicates were not established. A consumer cannot erase that limitation by attaching AVAILABLE/COMPLETE metadata later. Future immutable-byte support requires its own reviewed lifetime/retention boundary.
- **Stale/current use remains intentionally asymmetric.** Old receipt + old immutable capture may describe that named historical state. Old receipt + a new live read, mixed-generation pages, later correction or today's healthy archive cannot become the old capture. Conversely, an older capture must not suppress a new current integrity incident. Require an explicit named-historical request versus a current-freshness request, with different rejection rules.

The proposed ordered-event specification is useful as a RED contract but is not a PostgreSQL implementation test. Require actual gated MVCC/commit/cancellation/crash tests, durable publication checks and explicit consumer mapping before expanding the prototype's status. No host changes or PostgreSQL execution were performed in this review.
