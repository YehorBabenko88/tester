# Runtime component security status

The proposed production runtime is **CPython 3.14.10 x64**, **OpenSSL 3.5.9**, **PostgreSQL 18.7**, and 38 actual Windows wheels constrained by the existing platform versions and pinned by SHA-256 in `requirements-release-windows314.lock`. It is the only release ABI: `scripts/build_release.py` refuses any other private interpreter, because the installer installs only this lock. The former CPython 3.12.10 release lock was removed (issue #112); CPython 3.12 remains a development/CI interpreter only.

The [official Python 3.14.10 page](https://www.python.org/downloads/release/python-31410/) identifies a security release. The [official Windows documentation](https://docs.python.org/3.14/using/windows.html#the-nuget-org-packages) supports obtaining CPython through NuGet. The exact `python` 3.14.10 package was downloaded from the official NuGet service, its repository signature verified with Microsoft's signed NuGet verifier, and repository owners reported as CPython and steve.dower. The extracted executable has a Valid Authenticode signature from Python Software Foundation. Package SHA-256, certificate and source URLs are recorded in `python314-supplier-evidence.json`; verification output is retained separately.

The [PostgreSQL 18.7 release notes](https://www.postgresql.org/docs/18/release-18-7.html) document the current 18-series patch release observed during this audit. The [EDB binary download page](https://www.enterprisedb.com/download-postgresql-binaries?lang=en), linked by PostgreSQL's Windows distribution guidance, supplied the exact downloaded Windows binary archive. Its `postgres.exe` has a Valid Authenticode signature from EnterpriseDB Corporation. `postgresql-supplier-evidence.json` records the source, archive SHA-256 and signer. EDB's page did not publish an archive checksum: its recorded SHA-256 is a local content measurement, not an independently published vendor checksum. Authenticode on the executable does not authenticate every archive text/DLL file.

Only downloaded PostgreSQL bin/lib/share and license files are staged; no system cluster, service, port 5432 or data directory is touched. The private Python stdlib/DLL/runtime is copied without existing site-packages, then populated exclusively with the hash-locked offline wheelhouse. Isolated bootstrap imports of cryptography and venv pass. Every staged regular file is listed in the reviewed component pin map, included in the signed release inventory.

Dependency auditing covers Python distributions rather than stdlib, OpenSSL or PostgreSQL native vulnerabilities. Version/provenance and signatures reduce that gap but do not replace integrated security tests. Native SCM on both ABIs, full installer/database lifecycle, browser/recovery/reboot scenarios and independent acceptance remain required. Production signing remains blocked until the owner provides an independently trusted key; a test key never becomes production trust.
